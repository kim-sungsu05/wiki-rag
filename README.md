# RAG Toy Project: ドキュメントベースの Q&A システム

韓国の情報サイト「Namuwiki」の「RAG」に関するページを参照データとして活用し、RAGの動作原理を学習・実装しました。

---

<br>

### 📌 プロジェクトの概要と目的
* **RAG動作原理の習得**: Load、Chunking、Embedding、Retrievalに至るRAGパイプライン全過程の概念を理解し、実際にコードを書いて実装しました。
* **プロンプト上書きとLLMの制御**: Groq APIベースのLLMに検索されたコンテキスト（`context`）を注入し、提供されたドキュメントの内容のみに基づいて回答するようハルシネーション（Hallucination）を制御しました。

<br>

## 🛠️ 技術スタック
* **UI**: Streamlit
* **Framework**: LangChain (LCEL)
* **LLM**: Groq API (`groq/compound-mini`)
* **Vector DB**: FAISS
* **Embedding Model**: HuggingFace (`jhgan/ko-sroberta-multitask`)

* **[✅]** RAG性能評価基準の学習
<br>RAG 시스템의 성능 평가는 크게 검색(Retrieval), 생성(Generation), 그리고 시스템 운영(System) 3가지 영역으로 나뉜다

<br>

1. 검색 기능 (Retrieval Metrics):
    <br>질문에 맞는 올바른 문서 조각을 Vector DB에서 가져왔는지 평가 <br>(수치형태: 0.0 ~ 1.0 or 0% ~ 100%)

    * 문맥 연관성: 가져온 문서 중 질문과 실제로 관련 있는 내용의 비율
    * 검색 적중률: 상위 K개 문서 안에 정답이 되는 문서가 포함되어 있는지 여부
    * 순위 적절성: 정답에 가까운 가장 중요한 문서가 검색 결과의 최상단에 위치하는 지 여부

2. 생성 성능 (Generation Metrics)
    <br>LLM이 검색된 문서를 바탕으로만 정확하게 답변하는 지 평가 <br>(수치형태: 0.0 ~ 1.0 or 0% ~ 100%)
            
    * 근거성: 답변 내용이 오직 검색된 문서에만 기반하고 있는지 평가
    * 답변 연관성: 생성된 답변이 사용자의 원래 질문 의도와 부합하는지 평가
    * 답변 유사도: 준비된 정답 데이터셋이 있다면, 모델의 답변이 정답과 얼마나 일치하는지 평가

3. 시스템 및 비용 성능 (System Metrics)
    <br>실제 서비스 배포를 위한 성능 수치 <br>(수치형태: 초(s), 밀리초(ms), 달러($), 토큰(tokens)) | 800ms --> 0.8s
            
    * 응답 지연 시간: 질문 입력 후, 출력까지의 시간 및 전체 답변 생성 시간
    * 토큰 효율성: Chunk 크기와 개수에 따른 LLM 호출 비용 측정

<br>

    랭체인 기반 RAG 시스템은 표준 라이브러리를 활용하여 측정할 수 있다
    <br>Ragas: 랭체인과 가장 궁합이 좋은 평가 라이브러리

* **[✅]** ハイブリッド検索の概念学習
<br> 키워드 검색 (BM25)과 의미론적 검색 (Vector DB)의 두 장점만을 섞어서 검색 정확도를 극대화하는 기법을 하이브리드 검색이라고 한다

<br>

1. BM25(키워드 검색): 사용자가 입력한 단어(고유명사, 제품명 등)가 문서에 얼마나 자주 등장하는지 통계적으로 계산하여 찾아낸다

* 장점: 
    * 정밀한 고유명사 매칭: 제품 모델명, 전문용어, 사람이름, 코드번호 등 적확한 문자열 일치가 필요한 검색에 매우 강력
    * 빠른 속도와 저비용: 별도의 AI 임베딩 모델을 거치지 않고 단어 빈도 기반 통계 연산만 수행하므로 매우 빠르고 서버 자원을 거의 쓰지 않음
    * 결과 예측 가능성: 특정 문서가 왜 상위에 노출되었는지(어떤 단어가 몇 번 일치했는지) 명확히 추적하고 설명할 수 있다
* 단점: 
    * 어휘 불일치 문제: "자동차"로 검색하면 내용이 아무리 좋아도 "차량"이나 "승용차"라는 단어만 쓰인 문서는 찾아내지 못함
    * 오타 및 표현 변화에 취약: 띄어쓰기 오류나 오타가 발생하면 검색 정확도가 급격히 떨어짐


2. Vector DB: 단어가 다르더라도 문맥과 의미가 비슷한 문서를 찾아낸다

* 장점:
    * 문맥 및 의도 파악: 질문에 포함된 단어가 문서에 직접 등장하지 않더라도, 텍스트의 의미와 맥락이 통하는 문서를 찾아냄
    * 뛰어난 유연성: 동의어, 유의어는 물론, 오타나 다국어 질문에도 유연하게 대처
* 단점:
    * 고유명사 및 숫자 구분 미흡: ABC-101과 ABC-102처럼 단 한 글자 차이지만 의미적으로 유사해 보이는 고유 코드나 숫자를 명확히 구분하지 못하고 엉뚱한 문서를 들고올 수 있음
    * 연산 비용 및 속도: 텍스트를 벡터로 변환하는 임베딩 과정과 고차원 벡터 유사도 계산이 필요하여 CPU/GPU 자원을 더 많이 소모하고 응답 시간이 상대적으로 길어짐

<br>

    - 처음 RAG 개념이 퍼질 때는 '의미론적 검색'이 강조되었지만, 실무 현장에서는 키워드 검색을 단독으로 쓰거나 벡터 검색과 섞어서 쓰는 하이브리드 RAG가 가장 보편적이고 강력한 표준으로 자리 잡았다

    - 본문에서는 Vector DB와 의미론적 검색을 상응되는 단어처럼 작성했지만, 의미론적 검색은 개념/목적 Vector DB는 도구/수단이라는 점에서 차이가 있다
    의미론적 검색이라는 목적을 달성하기 위해 사용하는 대표적인 도구가 Vector DB이다
